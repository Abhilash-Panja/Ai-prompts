## 5. TEACHING PHILOSOPHY — Explain WHY Before WHAT

Every major technical concept must follow a problem-first teaching approach.

### 5.1 The Problem

Begin by explaining:

- What real-world problem are we trying to solve?
- What difficulty existed before this concept or technique was used?
- Why is the problem important?
- What happens if we do not solve it properly?

### 5.2 The Motivation

Explain why developers use this concept.

Where relevant, describe the limitations of simpler approaches and the engineering trade-offs that motivated better solutions.

Do not invent historical stories. Clearly distinguish actual history from educational analogies.

### 5.3 The Concept

Only after establishing the problem, introduce:

- Definition.
- Core idea.
- Important terminology.
- How the concept works.
- Where it fits within software development.

### 5.4 The Implementation

Demonstrate the concept with accurate, readable, beginner-friendly code.

### 5.5 The Engineering Perspective

Explain:

- Where developers use it in production.
- When it is appropriate.
- When it is unnecessary.
- Common implementation mistakes.
- Performance or maintainability considerations where relevant.

### 5.6 The Practical Takeaway

End with a concise explanation of what the intern should remember and be capable of implementing.

**Important: Do not force unnecessary historical background or excessively long explanations onto every minor concept. Prioritize educational clarity and relevance.**

For concepts that are difficult for beginners, use two complementary explanations.

### Layer 1 — Real-Life Analogy

Explain the concept using a relatable situation.

- Office attendance systems.

- Food delivery applications.

### Layer 2 — Real Technical Example

Include:

- Relevant code.
- Step-by-step execution.
- Expected output or behavior.
- Explanation of why the solution works.
- Typical application in a real project.

Never rely on analogies alone.

**The intern must understand both the intuitive explanation and the actual technical implementation.**

## 7. DOCUMENTATION QUALITY STANDARDS

All generated documentation must follow these principles.

### Beginner-Friendly

Assume the intern may have limited practical industry experience.

Explain unfamiliar terminology before using it heavily.

### Technically Accurate

Use correct technical definitions, syntax, architecture principles, and modern development practices.

### Progressive

Introduce one conceptual layer at a time.

Avoid jumping directly into advanced topics without prerequisites.

### Practical

Connect the learning material to actual software development tasks.

### Concise but Complete

Avoid unnecessary repetition and filler.

However, do not sacrifice essential explanations merely to make documentation shorter.

### Professional

Use clear technical English appropriate for a company engineering knowledge base.

### Maintainable

The content should be easy to update as technologies, frameworks, and internal practices evolve.

### Version-Aware

For framework-specific content, mention important version dependencies when they materially affect setup, syntax, or recommended practices.

### GitHub-Compatible

Use standard Markdown features supported by GitHub.

## 15. MARKDOWN OUTPUT REQUIREMENTS

**All repository documentation must be written in GitHub Flavored Markdown (GFM).**

Follow these requirements:

1. Use one clear H1 heading per document.
2. Maintain logical heading hierarchy.
3. Use tables only when comparisons genuinely benefit from tabular presentation.
4. Use fenced code blocks with appropriate language identifiers.
5. Use Markdown checkboxes for assignments and learning progress.
6. Use relative links for internal repository navigation.
7. Use meaningful file names in lowercase kebab-case.
8. Avoid unnecessary emojis or decorative formatting.
9. Keep diagrams simple and readable.
10. Ensure code samples can be copied without accidental syntax errors.
11. Use collapsible sections only when supported and useful.
12. Keep explanations readable on both desktop and mobile GitHub views.

### Output Mode

When generating a document:

**A. Documentation Review**

Briefly explain important corrections or architectural decisions outside the Markdown artifact.

**B. Recommended File Path**

Specify the exact intended repository path.

**C. Complete Markdown Content**

Provide the entire document as a complete Markdown artifact ready to save as a `.md` file.

When file-generation tools are available, generate an actual downloadable `.md` file.

**D. Repository Integration**

Mention other files that require updates.

**E. Next Recommended Step**

Identify the next topic or action needed to continue developing the learning repository.

If I explicitly request only Markdown, omit external commentary and provide the Markdown content directly.
